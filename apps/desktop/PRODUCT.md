# Product

## Platform

Windows, macOS, and Linux desktop (Electron)

## Users

NativePi serves people who want to get work done with an agent, including people who are not technically savvy:

- Existing Pi users who want a polished desktop workflow without losing Pi's capabilities, sessions, configuration, or extensions.
- People who want a graphical agent experience for projects and everyday work without needing developer or terminal knowledge.

Do not assume familiarity with Pi, coding agents, Git, branches, worktrees, command-line tools, or the app's architecture. Existing Pi users and developers remain important users, but their expertise must not be a prerequisite for the everyday interface. Advanced capabilities remain available through progressive disclosure.

NativePi is optimized for its primary desktop workflow. Accessibility is not a product goal, differentiator, or release criterion, and it does not justify adding redundant controls or alternate interaction paths that compromise the intended interface. Understandable everyday interaction is a product requirement for everyone.

## UI and UX Requirements

Read and apply this section before designing or implementing any new feature or UI enhancement. This includes technical features such as workspaces, code review, extensions, and background execution. Working backend functionality alone does not make a feature ready to ship.

- **Design around the person's task.** Start with what they want to accomplish and the next useful action. Do not turn backend options, state records, or implementation steps into a form the person must decipher.
- **Make the normal path simple.** Provide sensible defaults and one clear primary action for the current step. Users must not configure every available option before starting. Keep specialist controls in contextual settings or an advanced disclosure without removing their capabilities.
- **Use plain language.** Name actions by their outcome. Explain an unfamiliar concept briefly where it first matters; a technical label is not its own explanation. For example, offer a separate workspace with a short explanation of what happens to the current files, rather than assuming the person understands a Git worktree or starting ref. Keep precise technical terms available where an expert needs them.
- **Give each surface a clear purpose.** Keep starting work, configuring it, inspecting results, and browsing history distinct. Use focused dialogs, compact lists, and contextual details. Do not collect configuration, logs, history, permissions, and diagnostics in one long modal or dashboard.
- **Match the established app.** Use main's existing UI as the visual reference: its typography, spacing, density, alignment, control sizes, themes, and interaction patterns. Reuse the existing shadcn/base-ui primitives and shared pickers. Do not introduce raw browser selects or checkboxes, improvised disclosure controls, generic form stacks, redundant cards, or a separate visual style for each feature.
- **Keep everyday copy about the task.** Avoid walls of instructions, repeated caveats, implementation terminology, IDs, hashes, and internal state names in the normal flow. Put diagnostics, exact evidence, paths, and advanced configuration behind relevant details. Explain permissions, irreversible effects, and material limitations at the decision where the person needs them; keep those explanations concise and concrete.
- **Make state and recovery understandable.** Show what is happening, what finished, and what the person can do next. Empty, loading, running, failed, and completed states must be distinct. Errors need a useful recovery action. Preserve drafts, selections, and ongoing work while people navigate. Do not imply that an agent finishing means its work was verified or accepted.
- **Review the real experience.** Create, inspect, enhance, polish, and repeat. Compare the new surface with the established app in a running build, including representative empty, configured, running, result, and failure states. Check narrow layouts and light/dark appearances. Capture before/after evidence outside the repository. Passing tests or using the right component library is not evidence that the design is good.

Before calling UI work finished, verify that a person unfamiliar with the implementation can identify its purpose, take the main action, understand the result, and recover from a problem without an explanation from its developer. If the interface needs a tutorial to make its basic flow understandable, simplify that flow first. Preserve NativePi's calm, polished desktop character as features are added.

## Product Purpose

NativePi is a free, open-source desktop interface for the Pi coding agent. It gives Pi a focused graphical workflow for projects, conversations, model controls, tool results, diffs, authentication, settings, and extensions.

Success means NativePi is useful as the daily desktop interface for Pi project work: users can open a local project, authenticate, start or resume conversations, direct agent runs, inspect results, and manage relevant Pi capabilities without needing Pi's terminal UI.

## Positioning

NativePi is a Pi-based desktop coding-agent interface. Pi supplies model execution, providers, authentication, configuration, tool execution, queues, compaction, and sessions. NativePi adds built-in tools, instructions, and graphical workflows through Pi APIs. Useful app capabilities do not need separately installable extensions or matching Pi CLI behavior. Third-party Pi extensions remain supported.

## Chat and Work

NativePi offers two independent destinations. Work supports project folders and general work without a project. Project-free Work chats use a dedicated NativePi-managed working directory with normal Pi tools, configuration, and extensions. The managed directory is not a pinned project; its ordinary Pi sessions appear alongside project chats and can be filtered with “No project”. Chat starts without a project picker, using an internal working directory only because Pi requires one. Its transcripts remain ordinary Pi session files. Existing project conversations stay in Work; conversations cannot be transferred between destinations.

Chat folders are NativePi-owned organization metadata, with unique colors and persistent collapsed state. Chats appear inside their folders, and unfiled chats appear outside them. Moving a chat changes only its folder membership. Deleting a folder permanently deletes its chats after explicit confirmation; failed deletions retain the folder and remaining memberships.

The built-in Chat profile disables built-in edit/write tools, enables read-only exploration, and supplies conversational instructions. The shell remains available for diagnostics and information gathering; instructions against changes are behavioral guidance, not a sandbox. Automatic extension discovery, skills, templates, and context-file discovery are disabled in Chat. Settings → Tools & extensions → Packages can explicitly enable whole user extensions in their details, including their full tools. The profile still instructs Pi to avoid work tasks. Settings changes affect newly started Pi processes; restart Pi to update existing processes.

Built-in web access supplies Exa-backed web search and page reading in both destinations. Requests go directly from the user's machine to Exa's hosted MCP endpoint. No search account, API key, payment, or NativePi server is required. Exa's anonymous service is rate-limited and externally operated: NativePi honors retry timing, suppresses immediate retries during a cooldown, and reports unavailability without interrupting ordinary chat.

## Operating Context

- NativePi is a Windows, macOS, or Linux desktop application used alongside local code projects, Git repositories, and the existing Pi CLI ecosystem. Its workspace can be shared temporarily to a browser on the local network or through a temporary public link.
- Users pin project folders; create, discover, import, and manage Pi sessions; inspect streamed messages and tool activity; and review Git state and diffs.
- Existing Pi credentials, configuration, sessions, packages, skills, prompts, and extensions remain in Pi's normal storage and remain usable by the Pi CLI.
- NativePi keeps one Pi process per active chat, so chats in the same project and different projects may run concurrently. Git, terminals, trust, and Pi follow the folder of the open chat; the sidebar project filter only changes which chats are listed.
- Managed task workspaces offer explicit shared checkout or isolated branch/base selection, local setup/run/check actions, opt-in ignored-file copying, coordinated ports and conservative manual retirement. New delegate and automation worktrees share the inventory without automatic setup or trust. See `docs/task-workspaces.md`.
- Starting a new Work chat always offers a project chooser with “No project”, pinned folders, and an option to open another folder.
- Conversations open directly from Pi session files without waiting for a Pi process to start. Drafts remain editable and are restored if a cold send fails.
- Narrow windows move the context pane into a sheet. On a phone, project navigation moves there too so the conversation and composer remain usable.

## Current Capabilities

- User-created Work automations run once, daily or weekly with timezone-aware schedules, or watch an explicitly authorized GitHub repository/PR (or PR head branch) for new failed checks and submitted review feedback using authenticated gh polling. Every run uses the ordinary Pi host and a fresh Pi transcript, explicit model/reasoning/tier/tools, and a shared folder or retained Git worktree. Automation settings use compact saved rows, focused create/edit dialogs and contextual run history. The shared composer picker selects real models, reasoning and speed; execution options reveal workspace isolation and tool presets or Pi tool choices. Enable/pause/edit/delete/run-now/Stop and durable outcome history remain host-owned. The app must be running; missed slots are skipped and interrupted runs never replay. Completed turns require review, and three consecutive failures pause dispatch. See `docs/automations.md`.
- A built-in shared live browser in Work, including project-free chats. The Browser header button opens a dedicated native window for the current chat with bundled app-rendered tabs, navigation, theme/scale-aware controls and contextual human takeover; Pi's shipped `browser` tool lists, opens, navigates and closes up to eight HTTP(S) tabs, including local dev servers. Human and agent share the same live pages. Bounded semantic snapshots provide single-action references that expire on navigation, DOM changes or human interaction; agents can click, replace input text, select options, scroll, capture PNG images and read bounded console/load/network metadata. Tool evidence stays in ordinary Pi sessions. Remote pages run in sandboxed, isolated Electron web contents without Node, preload or NativePi APIs. Each chat has its own temporary cookies and tabs; closing the browser window hides it, while closing/restarting the owning Pi runtime clears them. Stop cancels only that chat's queued and active actions; delivered actions cannot be undone. Browser access does not change filesystem or shell permissions.
- Browser Take control (or the agent's handoff action) blocks agent observations and actions until the person explicitly resumes agent control. Sign-in, consent, sensitive input and cross-origin frame interactions belong to this human flow. Popups, downloads and device permissions are currently blocked; popup-only authentication is unsupported. Local Access can request that the host open its browser, but cannot display or remotely control the native browser window. Existing web search/page reading, sandboxed HTML artifacts and desktop computer use remain separate capabilities. No browser history, page content, passwords or cookies are persisted by NativePi as conversation state.

- Desktop voice dictation transcribes microphone audio locally with Whisper Large v3 Turbo. The first use offers an 886 MB model download with live progress and checksum verification; later dictation works offline. Audio is temporary, never uploaded or saved to Pi sessions. Transcripts enter the existing draft for review before sending. Browser Local Access does not expose dictation.

- Built-in computer use in Work, including project-free chats, through pinned, bundled agent-desktop. Pi tools read accessibility trees, operate apps, and capture screenshots returned to the model and stored in the ordinary Pi session. Mouse and keyboard actions can affect the real desktop. Work chats operate concurrently in different windows. Conflicting individual actions queue in arrival order; physical input and operations that affect the shared desktop serialize. References require a fresh snapshot after another chat changes their window. Stop cancels only that chat’s queued and active actions. Settings → Permissions → Computer use checks platform permissions and offers the macOS permission guide. Chat does not expose these tools.

- Optional next-message suggestions after successful turns, generated through Pi’s authenticated current model without changing the transcript. Tab accepts the suggestion as an editable draft; Escape dismisses it.
- Automatic names for new chats from the first user message, generated alongside the first turn through Pi's authenticated model runtime and saved as Pi session names without replacing manual names. Settings → General offers a separate title model, reasoning effort, and service tier. Automatic selection prefers connected GPT-6 Luna, Haiku 5.5, Gemini 4 Hydrogen, then Grok 4.7; it falls back to the saved Pi default or the lowest-priced catalog model from the first available provider. Explicit unavailable choices retain first-message titles.
- A shipped `ask_user` Pi tool with native choice and free-text dialogs, including explicit cancellation, plus service-tier selection beside reasoning in the composer model picker (also available through `/speed`) for supported OpenAI, Codex, and Anthropic transports.

- Work leads can assign fresh Pi delegates with explicit model, reasoning, supported service tier, and tool choices. Delegates share the working directory by default or work in an explicitly requested Git worktree. Delegate activity stays at its spawn call in the lead transcript. Delegate transcripts use a compact composer surface with static model/status and no editable input or configuration controls; leads handle progress, clarification, results, and follow-up work. Stop fences the owned group; Finish marks only idle groups Finished. Worktree integration remains explicit; managed workspace actions and retirement are available from Workspaces. See `docs/task-workspaces.md`.
- Work tools can discover/search/read historical threads without starting models, create independent leads, deliver durable peer inbox messages, explicitly wake selected messages, and stop/finish/delete Work threads. Inbox arrival alone never runs a model. Relationships and accepted messages live in versioned Pi custom records, and interrupted work never automatically resumes after restart. Desktop and Local Access share host-owned organization and orchestration snapshots. See `docs/orchestration.md` for tools and lifecycle details.
- Pinned, Focus, and Finished chat lists, project filtering, title and transcript search, and direct opening in installed editors or the system file manager.
- New, resume, rename, clone, fork, delete, import, HTML export, chat branches, and compaction workflows backed by Pi.
- Streaming text, thinking, tool activity, file-change summaries, rich diffs, retries, steering, follow-ups, queues, and abort controls.
- Images attached to a message by paste, drag and drop, or the file picker, resized by Pi before they are sent and shown in the transcript alongside the message they went with.

PNG, JPEG, GIF, and WebP images inside the project can appear inline; outside-project paths and remote image URLs are not loaded.

Snapshots live in Pi tool-result details and survive reopening or branching conversations. ## Conversation Workspace

Workspaces show one, two, or three independently selectable conversation panes, side by side or stacked, with resizable dividers and visible focus. Each pane owns its selected Pi session, transcript, composer, model controls, attachments, extension UI, and run state. A single app shell keeps Files, Source Control, terminals, trust, and project actions scoped to the focused pane’s cwd, including inspected delegates and worktrees. Delegates keep their read-only composer. Closing or unsplitting panes does not stop Pi runs.

Pane orientation, sizes, selections, and focus are NativePi-owned UI metadata saved locally for each desktop/browser origin. Pi session files remain authoritative. On narrow windows and phones, the active pane fills the workspace; pane buttons and next/previous shortcuts switch panes. Settings exposes rebindable pane navigation, split, and Jump to file shortcuts.

Files, transcript file links, working-file diff actions, and terminal file locations open a CodeMirror text/code editor. Files search and Jump to file search the active checkout using the existing project-file index. The editor supplies highlighting, line numbers, find, jump to line, undo/redo, and Markdown preview through the existing Markdown renderer. Save or Mod+S writes explicitly; dirty, saving, saved, conflict, and error states remain visible. Open in the preferred external editor remains available. Historical diffs stay read-only.

The host accepts existing UTF-8 files up to 1 MiB, rejecting binary/invalid text and paths or symlinks outside the supplied workspace. NativePi serializes its saves and compares content revisions before atomically replacing a file, checking again immediately before replacement. Ordinary filesystems cannot provide a transaction against arbitrary uncooperative external writers; this is not a cross-process file lock. Clean open files refresh from disk; dirty buffers retain edits and report changes. Conflicts require explicit reload/discard; there is no blind overwrite action.

Switching files, sessions, or projects retains unsaved buffers in memory. Closing a dirty file or reloading it requires discard confirmation; failed saves retain edits for retry. Browser unload warns about dirty files, and desktop quit names unsaved files in its existing confirmation. Buffers are not crash/reload recovery storage. Authenticated Local Access uses the same host validation and conflict checks. NativePi does not add a debugger, language server, or extension host.

## Boundaries and Constraints

- NativePi has a single authoritative local background host and a separately owned desktop window. Its light or dark appearance can follow the operating system or be selected explicitly, independently of its built-in or locally stored color scheme. Browser access requires an explicitly started server, the access token in the link, and the running background host. Remote Access is a throwaway Cloudflare quick tunnel created for one session and closed after twelve hours; NativePi does not operate a hosting service, register a permanent address, or hold an account of any kind.
- Pi session files are the durable conversation source of truth, including NativePi orchestration custom entries and attributed messages. NativePi’s automation journal persists explicit user-created automation intent, event cursors and transcript-linked run outcomes; it is not a conversation store. NativePi’s separate UI state persists pinned projects and chats, the last project and chat, text drafts, favorite models, pane state, source-control preferences, local review metadata and references to Pi reviewer sessions, and its own interface preferences.
- Pi remains the agent runtime. NativePi ships its own tools and instructions through Pi APIs, including Chat mode, web access, inline HTML artifacts, chat naming, ask_user, and service-tier controls. Subscription capacity is reported for the provider connections listed above; throughput guidance is not shipped. Orchestration runs through Pi APIs in Work; Chat retains its existing profile.
- Agent configuration is Pi's. NativePi reads and writes it through Pi's own settings manager at user scope, so a change made here is a change the Pi command line sees; NativePi never writes Pi's configuration format itself, and exposes only the settings that have meaning in a desktop window. Project-scope overrides remain the Pi command line's business.
- Authentication is Pi-backed. Credentials are never stored in NativePi renderer persistence or its state file.
- Git mutation is deliberately narrow: branch checkout and creation require a clean worktree, and worktrees may be added. NativePi can stage or unstage files and individual hunks, revert an unstaged tracked file from the index after confirmation, create commits, push the current branch, fast-forward it before pushing, and open a GitHub pull request through `gh`; it can ask Pi to draft commit wording in a separate ephemeral run that loads the user's normal project instructions. File reversion preserves staged changes and does not delete untracked files. NativePi does not create merge commits, rebase, create checkpoints, or rewrite history.
- Graphical extension handles belong to one pane selection and runtime binding; stale callbacks reject rather than targeting another chat. Optional host capability requirements report incompatibility before mounting. Pi-side graphical connections can be disposed during session shutdown. See `packages/extension-api/COMPATIBILITY.md` for tested coverage and limits.
- Normal Pi extensions run unchanged. Optional graphical extensions contribute only through controlled NativePi UI slots and are trusted code, not sandboxed code.
- Terminal extension components are drawn by Pi and displayed, not reimplemented: NativePi runs the component in the Pi process and shows what it draws, so it looks as its author wrote it rather than as NativePi would have styled it. Two parts of Pi's terminal UI have no equivalent here and keep Pi's documented no-op: raw terminal input, and replacing the input editor, which in this window is the composer.
- NativePi has no cloud sync, collaboration, remote projects, SSH launching, product accounts, paid features, or NativePi-owned telemetry. Pi's own optional anonymous usage analytics remain configurable through Pi's configuration; NativePi does not expose analytics controls in its settings screen.
- Usage totals are local estimates recorded in Pi session files, not provider invoices.
- Project management is in the project actions menu beside the sidebar project filter. Chat management uses row context menus opened by right-click; marking a chat finished or returning it to Focus also has a direct row action.
- NativePi is MIT licensed. GitHub publishes a Windows NSIS installer, macOS x64 and arm64 DMG/ZIP builds, and Linux x64 and arm64 AppImages. Builds are currently unsigned and macOS builds are not notarized, so Windows SmartScreen and macOS Gatekeeper warnings are expected.
- Release automation checks the Unreleased changelog daily for stable releases and publishes eligible main changes as Nightly prereleases. The schedule, version format, and maintainer configuration are documented in [`docs/release.md`](../../docs/release.md).

## Brand Commitments

- The product name is NativePi.
- Product language should be direct, calm, and understandable without assuming Pi or terminal expertise.
- The product should feel focused and capable rather than hiding advanced behavior or overwhelming the basic path.
- Pi must be named accurately as the agent that owns and performs agent work.

## Evidence on Hand

- `src/` is the source of truth for implemented behavior; this document records the durable product boundary rather than a speculative roadmap.
- `package.json`, `electron.vite.config.ts`, and `components.json` record the current runtime, build stack, dependencies, and shadcn baseline.
- No testimonials, customer logos, usage benchmarks, pricing claims, press coverage, or commercial proof assets are available and future work must not fabricate them.

## Product Principles

1. Pi is the product core: call Pi and present its result instead of rebuilding its behavior.
2. Assume no technical expertise in everyday workflows; keep advanced Pi capabilities available through progressive disclosure.
3. Protect local work: keep Pi sessions authoritative, preserve drafts, and fail conservatively around external session changes.
4. Prefer direct, understandable behavior over speculative infrastructure or hidden automation.
5. Keep user trust explicit through local-by-default operation, no NativePi-owned telemetry, honest extension trust boundaries, and narrowly scoped Git operations.

## Accessibility Scope

Accessibility is not a product objective or a reason to expand visible interface chrome. NativePi does not add redundant controls, alternate workflows, or special presentation solely to satisfy accessibility audits.

Standard semantic desktop controls, keyboard operation, visible focus treatment, and correct dialog, menu, field, and sheet behavior remain baseline implementation quality. These requirements must preserve intentional product interactions, including the left sidebar's right-click-only chat management menus. Product copy must not require prior familiarity with Pi's terminal interface.

## Independent code review

Source Control offers independent multi-file Pi reviews with explicit uncommitted, staged, selected-file and branch-versus-base scopes. Host-owned jobs retain progress, interruption/error outcomes, exact reviewed patches, skipped inputs and ordinary Pi transcript references. Reviewers have repository read/search tools; shell checks require explicit unsandboxed-shell permission. Fix requests prepare drafts in a selected Work chat; fresh verification names concerns and retains verdict/evidence history without automatically resolving them. Input staleness, current anchors, check results and human acceptance remain separate. See [code review](../../docs/code-review.md) for limits and integration boundaries.
